# Signaling-протокол media-server

## Подключение

`ws(s)://<host>/ws?roomId=<uuid комнаты из backend>&peerId=<id вкладки>`

`peerId` — опциональный стабильный идентификатор клиента (uuid, живёт в sessionStorage
одну вкладку). По нему сервер опознаёт вернувшегося участника.

## Формат сообщений

```
Запрос C→S:   { "id": 1, "method": "join", "data": { ... } }
Ответ S→C:    { "id": 1, "ok": true, "data": { ... } }              
              { "id": 1, "ok": false, "error": "...", "code": "..." }
Уведомление:  { "notification": "newPeer", "data": { ... } }   — в обе стороны, без ответа
```

id генерирует клиентом (инкремент), сервер копирует его в ответ.Запросы можно слать параллельно, не дожидаясь ответов.

## Методы

| Метод                    | Запрос                                          | Ответ                                                             |
| ------------------------ | ----------------------------------------------- | ----------------------------------------------------------------- |
| join | { displayName } | { rtpCapabilities, peers: [{id, displayName, detached, producers: [{producerId, kind, source, paused}]}], iceServers, resumed, transports: [{id, direction}] } |
| leave                   | {} — выхожу навсегда, сессию снять сразу        | {} — страховка к close-коду 1000 на случай потерянного фрейма   |
| createWebRtcTransport  | { direction: "send"\|"recv" }                 | { id, direction, iceParameters, iceCandidates, dtlsParameters } |
| connectWebRtcTransport | { transportId, dtlsParameters }               | {}                                                              |
| restartIce             | { transportId }                               | { iceParameters } — свежие параметры для transport.restartIce() |
| produce                | { transportId, kind, rtpParameters, source? } | { id } — id нового producer                                     |
| consume                | { transportId, producerId, rtpCapabilities }  | { id, producerId, peerId, kind, rtpParameters, source }         |
| resumeConsumer         | { consumerId }                                | {}                                                              |
| pauseProducer | { producerId } | {} |
| resumeProducer | { producerId } | {} |

Правила:

- до join все методы кроме join → Not joined
- повторный join **на том же соединении** идемпотентен: сервер просто возвращает
  текущее состояние комнаты (клиент так переживает ретраи после сбоя);
  join с другого соединения — это новый участник
- source в produce: "webcam" (default) | "screen"
- повторный createWebRtcTransport с тем же direction закрывает старый транспорт(используется при переподключении)
- consume создаёт consumer **на паузе**: клиент получил ответ → собрал track →вызвал resumeConsumer. Так не теряются первые RTP-пакеты.
- restartIce запускает ICE restart серверного транспорта (медисуп ≥3.13):
  клиент должен передать полученные iceParameters в свой transport.restartIce() —
  это штатный способ оживить транспорт после смены сети, не пересоздавая его

Ошибки join: room_not_found, room_closed, room_full (в поле code).

### Коды закрытия signaling-сокета

Клиент закрывает сокет разными кодами — сервер по ним отличает намеренный
выход от обрыва сети:

| Код | Значение | Реакция сервера |
| --- | -------- | ---------------- |
| 1000 | «ухожу навсегда» (кнопка «Выйти», pagehide) | участник убирается сразу, остальные получают `peerClosed` мгновенно |
| 4001 | «пересобираю соединение, вернусь» (смена сети, watchdog) | сессия живёт в grace-периоде |
| 4000 | «replaced» — сервер сам закрыл старый сокет при resume | особый случай (см. ниже) |
| 1006 / 1005 | close-фрейма не было (сеть умерла) или старый клиент | сессия живёт в grace-периоде |

Метод `leave` — то же, что close(1000), но надёжнее: запрос долетает даже
если close-фрейм потерялся. Клиент шлёт оба.

### Resume: участник вернулся с тем же peerId

Сессия участника переживает обрыв signaling-сокета. Пока не истёк
`PEER_DETACH_GRACE_MS` (по умолчанию 30 с) после **непреднамеренного**
обрыва (код 4001/1006 — смена сети; намеренный выход кодом 1000 убирает
участника сразу), сервер хранит его транспорты, producers и consumers,
а остальным участникам **ничего не рассылает** — с их точки зрения
участник не уходил. 30 с с запасом перекрывают возврат wifi на телефоне
после смерти мобильной сети (переассоциация радиомодуля занимает 10–30 с).

Если участник отсутствует дольше `PEER_DETACH_NOTIFY_MS` (по умолчанию
5 с — короче мигают обычные быстрые resume за 1–3 с), остальным уходит
`peerDetached` — его плитка показывает «переподключается…» вместо
замершего кадра. При возврате — `peerResumed`, бейдж снимается.

Если при join в комнате уже есть участник с таким peerId (старое соединение
умерло или ещё «выглядит живым» — при смене сети сервер может не успеть это
заметить), сервер:

1. переносит всю медиа-сессию на новое соединение: join-ответ приходит с
   `resumed: true` и списком живых `transports` — клиенту достаточно
   `restartIce` для них (новый DTLS не нужен), полная пересборка — запасной
   план, если выживших нет или рестарты не помогают;
2. рвёт старый сокет **close-кодом 4000 ("replaced")** — живая старая вкладка
   останавливается, а не воюет за комнату;
3. `newPeer` остальным НЕ шлётся (участник не «исчезал» и не появлялся заново).

Не вернулся за grace-период — обычный выход: close сессии и `peerClosed`
всем остальным. Повторный join **на том же соединении** также идемпотентен
и отвечает `resumed: true` + `transports` — так дешево проходит восстановление
по mediaStalled без обрыва сигналинга.

Лимит участников (room_full) проверяется после resume — «призрак» не занимает место.

## Уведомления S→C

| notification     | data                                                          |
| ---------------- | ------------------------------------------------------------- |
| newPeer        | { peerId, displayName }                                     |
| peerClosed     | { peerId } — участник вышел, убрать все его треки           |
| peerDetached   | { peerId } — связь с участником потеряна, он может вернуться: плитка ждёт (бейдж «переподключается…») |
| peerResumed    | { peerId } — участник вернулся на новом соединении, бейдж снять |
| newProducer    | { peerId, producerId, kind, source } — можно делать consume |
| producerClosed | { peerId, producerId } — источник выключен/заменён          |
| consumerClosed | { consumerId } — ваш consumer умер (источник пропал)        |
| producerPaused | { peerId, producerId } — источник на паузе (mute / камера выкл) |
| producerResumed | { peerId, producerId } — источник снова активен |
| ping           | {} — метка живого соединения (см. «Переподключение»), клиенту наверх не отдаётся |
| mediaStalled   | { producers: [{ producerId, kind, source }] } — сервер не получает ваше медиа |

## Переподключение

Клиент держит стабильный peerId (один на вкладку) и при обрыве:

1. сам переподключает WebSocket (экспоненциальная задержка, мгновенная попытка
   по событию `online`, HTTP-проба ожившей сети);
2. заново выполняет join с тем же peerId — сервер возобновляет сессию
   (`resumed: true`, транспорта живы), остальные участники ничего не замечают;
3. оживляет выжившие транспорты `restartIce` (нового DTLS не нужно) и
   ресинкает список участников/производителей; полная пересборка — запасной
   план (перезагрузка вкладки, рестарты не помогли): она переиспользует живые
   локальные треки, а createWebRtcTransport заменит старые транспорта.

Мёртвые соединения сервер ловит heartbeat-пингами каждые 10 с (terminate,
если два цикла подряд нет ответа; браузеры отвечают на ping автоматически) —
на случай, когда клиент не успел переподключиться, а сокет «завис».

### Смена сети без обрыва signaling (мобильный ↔ wifi)

Signaling-сокет может пережить смену сети, а вот медиа-транспорты — нет:
получится «частично живой» участник (входящее видит, исходящее у остальных
заморожено). Две защиты:

1. **Сервер**: раз в `MEDIA_HEALTH_INTERVAL_MS` (по умолчанию 5 с) проверяет
   score всех активных (не paused) producers участника. Если все нулевые
   `MEDIA_STALLED_TICKS` проверок подряд (по умолчанию 2) — участнику уходит
   `mediaStalled`. Клиент должен пересобрать транспорты: сперва дёшево —
   `restartIce` для проблемного транспорта, если не помогло — полный re-join
   по живому соединению (join идемпотентен, createWebRtcTransport заменит
   старые транспорты).
2. **Клиент**: слушает `connectionstatechange` транспортов; при `failed` —
   ICE restart сразу, при `disconnected` — через 5 с. Не ожил за 10 с —
   полный re-join.

### Half-open соединения

Protocol-уровневые ping-и браузер не отдаёт странице, поэтому сервер
продублирует их сообщением `ping` каждые `SIGNALING_PING_INTERVAL_MS`
(по умолчанию 5 с). Клиент держит watchdog: нет сообщений дольше трёх
интервалов — соединение считается мёртвым и пересоздаётся, не дожидаясь
`onclose` (при смене сети его может не быть вовсе).

Смена **типа** сети (wifi ↔ cellular) на Android часто не даёт `offline`/
`online`, поэтому клиент дополнительно слушает `navigator.connection`:
смена `type` (Android/ChromeOS) или `effectiveType` (доступен и на
десктопе) немедленно форсирует переподключение. Ложная тревога дёшева —
сервер возобновит сессию без пересборки. Пока `navigator.onLine === false`,
клиент новых сокетов не открывает — ждёт `online` (периодически
перепроверяя флаг).

### Проба сети

Событие `online` ненадёжно: при смене wifi ↔ мобильный интернет его может
не быть вовсе (Firefox, iOS), а когда оно приходит, новая сеть ещё не
готова — первая же попытка проваливается, и дальше клиент досиживает
остаток backoff-таймера. Поэтому в цикле переподключения клиент раз в
секунду делает лёгкий HTTP-запрос на тот же origin
(`GET /?netprobe=<ts>`, `cache: no-store`, таймаут 2.5 с). Сам факт
ответа — даже 4xx/5xx — значит, что маршрут до сервера жив: backoff
сбрасывается и подключение происходит немедленно (свежую попытку младше
1.5 с проба не срывает).

Та же проба ускоряет ловлю half-open-соединений: если открытое соединение
молчит дольше 7 с (сервер пингует каждые 5 с — столько молчать он не
может), но HTTP-проба проходит — сокет мёртв, и клиент пересоздаёт его,
не дожидаясь полного порога тишины (15 с). Если проба не проходит —
сети нет, спешить некуда: клиент остаётся в цикле ретраев.

Все запросы клиент сопровождает таймаутом (10 с): потерянный ответ не
должен подвешивать восстановление.
